# cv-graphql

Цифровая визитка Максима Ситникова: бэкенд на NestJS, GraphQL и Prisma.
Через Apollo Sandbox можно получить профиль, навыки, опыт работы и проекты.

- Демо: `https://<имя-сервиса>.onrender.com/graphql` (ссылка появится после деплоя)
- Стек: TypeScript, Node.js 24, NestJS 11, GraphQL (Apollo Server 5, code-first), Prisma 7, PostgreSQL 17, Docker

## Быстрый старт

Нужен только Docker.

```bash
git clone https://github.com/yellow444/cv-graphql.git
cd cv-graphql
docker compose up --build
```

Откройте http://localhost:3000/graphql, там Apollo Sandbox с готовым запросом.
Контейнер приложения при старте сам применяет миграции и заполняет базу, ручных шагов нет.

- Порты по умолчанию: 3000 для приложения и 5432 для PostgreSQL (только на 127.0.0.1).
  Если они заняты: `APP_PORT=3001 POSTGRES_PORT=5433 docker compose up --build`.
- Остановить: `docker compose down`. Удалить и данные базы: `docker compose down -v`.
- Проверка живости: `curl http://localhost:3000/health`.

## Примеры запросов

Запрос из задания:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Всё сразу, с вложенными достижениями и фильтром навыков по группе:

```graphql
query {
  profile {
    name
    title
    links {
      label
      url
    }
    skills(category: DEVOPS) {
      name
      note
    }
    experience {
      company
      position
      period
      startDate
      endDate
      achievements
    }
    projects {
      name
      url
      stack
    }
  }
}
```

Из терминала:

```bash
curl -s http://localhost:3000/graphql \
  -H 'content-type: application/json' \
  -d '{"query":"{ profile { name skills { name } } }"}'
```

Полная схема лежит в [`schema.gql`](schema.gql), описания полей видны и в Sandbox.

## Архитектура и решения

### Слои

Каждый раздел визитки (профиль, навыки, опыт, проекты) живёт в своём модуле NestJS, внутри три слоя:

- **Резолвер** знает только про GraphQL: корневой запрос, вложенные поля, аргументы. Логики и обращений к базе в нём нет.
- **Сервис** отвечает за правила: группирует записи по родителю, превращает строки базы в объекты API, считает период работы, фильтрует навыки по группе, решает, что делать, если профиля нет.
- **Репозиторий** единственный, кто ходит в Prisma. Каждый метод это один SQL-запрос.

GraphQL-модели (`*.model.ts`) служат и типом ответа сервисов, как в документации NestJS. Для визитки этого достаточно. Если API и внутренняя модель разойдутся, у сервисов появятся свои типы, а преобразование переедет в резолверы.

### Схема GraphQL

- Один корневой запрос `profile: Profile!`. Визитка про одного человека, поэтому без аргументов. В базе при этом у всех дочерних таблиц есть `profile_id`, так что запрос `profile(slug:)` добавляется парой строк.
- Code-first: типы описаны TypeScript-классами с декораторами, SDL строится автоматически. Вне продакшена схема пишется в `schema.gql`, и изменения API видны в git diff.
- Навыки отдаются плоским списком с полем `category` (enum) и необязательным фильтром `skills(category: ...)`. Запрос из задания `skills { name }` работает как есть, а сгруппировать по `category` клиенту несложно.
- У навыка есть поле `note` для честных оговорок: например, у Kafka стоит «мало». Уровни владения намеренно не заведены, чтобы не придумывать оценки.
- Период работы хранится годом и месяцем в отдельных колонках, месяц может быть пустым, если известен только год. API отдаёт `startDate` и `endDate` в ISO 8601 с той точностью, что известна (`2021-09` или `2023`), и готовую строку `period`. Если дата окончания не указана, `endDate` равен `null`, а `period` выглядит как «с 09.2021». Это значит «дата не указана», а не «по настоящее время».
- Достижения это `achievements: [String!]!`. В базе они в отдельной таблице с порядком показа.
- Схема без циклов: у профиля есть разделы, а у разделов только скалярные поля (у опыта ещё список строк). Глубина любого запроса ограничена самой схемой, поэтому отдельный лимит глубины пока не нужен.

### Вложенные данные без N+1

Каждое вложенное поле резолвится отдельно. Без батчинга запрос «опыт и достижения» сделал бы один SELECT на каждое место работы: классическая проблема N+1.

Здесь все вложенные поля грузятся через [DataLoader](https://github.com/graphql/dataloader). Резолвер вызывает `loader.load(id)`, DataLoader собирает все id за один тик и вызывает сервис один раз, а репозиторий делает один запрос `WHERE parent_id IN (...)`. В итоге любой запрос стоит фиксированное число SQL-запросов, по одному на уровень: полный запрос визитки это 6 запросов (профиль, ссылки, навыки, опыт, достижения, проекты), сколько бы ни было мест работы. e2e-тест проверяет это по журналу запросов Prisma.

Загрузчики создаются заново на каждый GraphQL-запрос в контексте Apollo (`LoadersFactory.create()`). Кэш DataLoader не живёт дольше запроса, поэтому данные разных запросов не смешиваются. При этом провайдеры NestJS остаются синглтонами: request-scoped провайдеры сделали бы request-scoped всю цепочку зависимостей и пересоздавали её на каждый запрос.

Почему не `include` в Prisma. Чтобы загрузить всё одним вызовом в корневом резолвере, пришлось бы либо всегда тащить все связи, даже когда клиент просит только `name`, либо разбирать AST запроса и строить `include` динамически. DataLoader загружает только запрошенные поля, код остаётся простым, а число запросов не зависит от объёма данных. Бонус: `skills` и `skills(category: DEVOPS)` в одном запросе используют один SQL-запрос, фильтр применяется в сервисе.

### База данных

- Prisma 7 с драйвер-адаптером `@prisma/adapter-pg`: клиент без бинарного движка запросов. Клиент генерируется в `src/generated/prisma` при `npm install` и сборке и в git не хранится.
- У каждой дочерней таблицы индекс `(parent_id, sort_order)` под запрос загрузчика и каскадное удаление вместе с родителем. Уникальные ключи `(profile_id, name)` у навыков и проектов и `(profile_id, url)` у ссылок не дают появиться дублям даже при ошибке в коде.
- Порядок показа задаёт колонка `sort_order`, она берётся из порядка элементов в файле данных.
- Схема меняется только миграциями из `prisma/migrations`, на старте они применяются через `prisma migrate deploy`.

### Инициализация и заполнение базы

Контейнер стартует скриптом `docker-entrypoint.sh`: применить миграции, выполнить сид, запустить приложение (через `exec`, чтобы Node получал SIGTERM). Каждый шаг идемпотентен, контейнер можно перезапускать сколько угодно.

Данные визитки лежат в `prisma/seed/profile.data.ts` и типизированы (`profile-seed.types.ts`), логика сида отдельно, в `seed-profile.ts`. Сид работает так:

1. Всё в одной транзакции под `pg_advisory_xact_lock`: два экземпляра, стартующие одновременно, не запишут данные дважды.
2. Считается SHA-256 от данных. Если он совпадает с сохранённым в служебной таблице `seed_state`, сид ничего не пишет. Поэтому перезапуск не трогает базу, и id записей не меняются.
3. Если данные изменились, профиль обновляется по `slug` (upsert), а дочерние записи заменяются целиком. Файл данных единственный источник правды: удалённый из файла навык пропадёт и из базы, дублей не бывает.

Замена целиком проще, чем upsert каждой строки по естественному ключу, и сразу удаляет лишнее. Цена: при изменении данных у дочерних записей меняются id. Для визитки это неважно. Если появится редактирование через API, сид нужно будет перевести в режим «заполнить, только если пусто».

Корректность данных сида проверяет unit-тест: уникальность ключей, валидные периоды, только https-ссылки.

### Конфигурация

`@nestjs/config` и схема на zod (`src/config/env.validation.ts`). С неполной конфигурацией приложение не стартует и сразу называет переменную. Переменные: `DATABASE_URL` (обязательна), `PORT` (по умолчанию 3000), `NODE_ENV`.

### Apollo Sandbox в продакшене

Sandbox здесь это интерфейс визитки, поэтому он включён везде: плагин `ApolloServerPluginLandingPageLocalDefault` с встроенной песочницей и `introspection: true`. GET `/graphql` из браузера отдаёт Sandbox, POST обрабатывает запросы. Защита Apollo от CSRF включена по умолчанию. API только на чтение и без cookie, поэтому CORS открыт.

### Docker

- Многоэтапная сборка: `deps` ставит зависимости (слой кэшируется, пока не меняются `package-lock.json` и схема), `build` собирает код и убирает dev-зависимости, `runtime` на `node:24-alpine` содержит только собранный код, prod-зависимости и миграции и работает от пользователя `node`.
- `HEALTHCHECK` ходит в `/health`, который проверяет и базу.
- В образе есть Prisma CLI, потому что миграции применяются при старте контейнера: на бесплатном тарифе Render нет отдельной команды перед деплоем. CLI занимает большую часть `node_modules`. Если вынести миграции в отдельный шаг (pre-deploy команда Render, Job в Kubernetes или отдельный сервис в compose), CLI из итогового образа можно убрать и сильно его уменьшить.

### Версии и инструменты

- Все версии зависимостей закреплены точно.
- NestJS 11, а не 12: ветка 11 поддерживается, а NestJS 12 перешёл на ESM-only, что усложняет Jest и не даёт выигрыша для этой задачи.
- Jest компилирует тесты в CommonJS (`tsconfig.spec.json`): Prisma 7 загружает свой WASM-компилятор запросов через `import()`, который Jest без экспериментального флага не поддерживает. Сборку приложения это не затрагивает.
- `overrides` в `package.json` поднимает `@graphql-tools/utils` до версии с исправлением уязвимости (NestJS GraphQL 13 закрепил старую).
- `npm audit` показывает одно предупреждение в `multer`, зависимости `@nestjs/platform-express`. Загрузка файлов в проекте не используется. Исправление вышло недавно, обновлю вместе со следующим патчем NestJS.

## Деплой на Render

Вариант 1, Blueprint (всё по `render.yaml`):

1. Render Dashboard, **New**, **Blueprint**, подключить репозиторий GitHub.
2. Render создаст PostgreSQL `cv-graphql-db` и веб-сервис `cv-graphql` из Dockerfile, `DATABASE_URL` подставится сам.
3. После деплоя открыть `https://<имя-сервиса>.onrender.com/graphql`.

Вариант 2, вручную:

1. **New**, **Postgres**: регион Frankfurt, план Free. После создания скопировать **Internal Database URL**.
2. **New**, **Web Service**: этот репозиторий, Language **Docker**, тот же регион, план Free.
3. Environment: `DATABASE_URL` равен Internal Database URL. `PORT` Render задаёт сам, приложение его читает. `NODE_ENV=production` уже стоит в Dockerfile.
4. Advanced, Health Check Path: `/health`.
5. Deploy. При старте контейнер сам применит миграции и сид, в логах будет `Profile "maksim-sitnikov": created`.

Особенности бесплатного тарифа: сервис засыпает после простоя, и первый запрос после сна идёт около минуты. Бесплатная база Render работает ограниченный срок, условия есть в документации Render.

## Что можно добавить

- **S3 для файлов.** Аватар и PDF-резюме в S3 (локально MinIO в docker-compose), в API поле `avatarUrl` с подписанной ссылкой.
- **Мутации с авторизацией.** Редактирование визитки через API под JWT-guard, сид в режиме «только если пусто».
- **Кэширование.** Данные меняются редко: HTTP-кэш для GET-запросов, response cache Apollo или Redis, persisted queries.
- **Ограничение сложности запросов**, когда появятся списки с пагинацией и циклы в схеме.
- **CI в GitHub Actions**: lint, typecheck, unit и e2e с PostgreSQL как service, сборка образа.
- **Наблюдаемость**: структурные логи (pino) и метрики для Prometheus.
